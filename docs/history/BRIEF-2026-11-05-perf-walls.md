## 0. 一句话背景

ScalarWide 是一个纯标量的**定宽大整数**库（Java 25 工具链 / release 21），提供
`Wide128/256/384/512/768/1024` 六个宽度：扁平小端 limb 表示、二补码、模 2^N 回绕、
`compareTo` 无符号、`mul/mulHigh/mulFull` 分别表达低半/高半/全积。
用途是"宽域坐标 / 大数 map key"（Minecraft 类工作负载，坐标可达 2^53 甚至 1e306）。

项目已 `1.0.0` 冻结、维护模式：只接受 bug 修复、**消费者驱动**的性能优化、纯增量 API。
纪律（硬性）：**先测后改**；一次一个变量；JMH 是唯一证据；比值必须标口径；
BigInteger 只作正确性 oracle，不作性能对照（同场景对照 = BouncyCastle `math.raw.Nat*`）。

实现现状（关键）：**没有 Karatsuba，没有 SIMD，没有数组表示，没有目的缓冲 API。**
表示层是"16 个 `final long` 字段 + 全展开直写"；`Limbs` 是被测的参考引擎 + 内部 oracle。

## 1. 已经做完的两轮（供判断"还剩什么"）

### Round 1 — `toBigInteger` 单趟字节桥

`Limbs.toBigInteger(long[])` 原来是 `v = v.shiftLeft(64).or(limb)` 逐 limb 循环（二次复杂度）。
六个宽度的 `toBigInteger()` + `toString()` + `toHexString()` 全汇聚在这一个方法。

改成"limb 向量一次性铺成大端字节 + `new BigInteger(1, be)`"后（锁核，同机同命令）：

| | 改前 ns | 改后 ns | 倍数 | B/op |
|---|---|---|---|---|
| toBigInteger256 | 242.7 | 32.8 | 7.4× | 1216 → 184 |
| toBigInteger512 | 603.5 | 48.7 | 12.4× | 2960 → 280 |
| toBigInteger1024 | 1146.4 | 59.3 | 19.3× | 5840 → 472 |
| toDecimalString1024 | 6209.9 | 4812.2 | 1.29× | 14456 → 9088 |
| toHexString1024 | 6932.9 | 5715.1 | 1.21× | 15697 → 10328 |

### Round 3 — 1024 `mulHigh` 内层去 16-way switch

原实现（全库**唯一**还在循环体内用运行时索引访问器的热方法）：

```java
for (int i = 0; i < 16; i++) {
    long ai = limb(i);                 // 16-way switch
    for (int j = 0; j < 16; j++) {
        long bj = o.limb(j);           // ← 256 次 16-way switch，在最内层
        ...
    }
}
```

内层展开为 16 段直读字段（常量偏移）后：**529.6 → 367.8 ns（−30.6%），分配不变（416 B/op）**。

同 run 内被否决的两个中间方案：
- 把 `o` 的 limb 提到局部 `long[] b` → 392.6 ns / **560 B**（白扔 144 B）；
- `mulHighComposed`（9 个 256-bit 块 + 装配）→ **431.0 ns / 1328 B**（更慢且垃圾多 2.4×）——
  独立复现了 2026-10-11 P16 的否决结论。

## 3. 六堵墙

### 墙一：ALU 已经不是瓶颈，所有算术优化的靶子都空了
1024 `and`（就 16 条 AND）要 13.64 ns ≈ 60 周期；同档 `compare` 0.75 ns、`hash` 4.31 ns、都 0 分配。
**结论**：add/sub/and/shl 的成本 ≈ 分配 144 B + 写回，算术占比很小。这堵墙只能绕过，不能穿。
继续调进位公式/指令数/展开度，上限是个位数百分点。

### 墙二：JIT 的 325 B 内联预算决定"谁是垃圾"
同一原子、同一套乘法，两条调用边界两个世界：

| | 调用边界 | B/op |
|---|---|---|
| `512.mul` | `mulFull` **返回对象**（EA 吃得掉） | **80** |
| `768.mul` | `mulFullInto8(s,…)` 传 `long[36]`（内核 1509 B 不可内联 → 数组逃逸） | **416** |
| `1024.mul` | 同上，`long[64]` | **672** |
| `768.mulHigh` | `long[72]` + `long[12]` | **816** |

**这是数组 vs 对象的假问题，真问题是调用边界。** 全库最大的一处结构不对称。

### 墙三：进位链延迟（Java 没有 `adc`）
1024 `mulHigh` 367.8 ns / 256 个乘积 = **6.2 cycle/乘积**；HotSpot `multiplyToLen` 内建 ≈ **2**。
差的不是 uop 数，是**行内 16 级串行进位链的延迟无法隐藏**。
三条平行路线已全部实测否决：列累加三进位元（P16，+52%）、块组合（P16 + 本轮 431 ns/1328 B）、
单巨方法（Round H）。Java 能表达 carry-save，但活跃值（3 组 × N 列）溢出寄存器。

### 墙四：Karatsuba 在这个 API 面上无处落脚
`mul`/`mulHigh` 都是**半积**；全积 API 最高只到 `mulFull(256)`。而 Karatsuba 的 3 块分解产出全积。
低半 `mul` 也不领情：1024 低半只需 4×4 块里的 10 块 = 160 肢积，Karatsuba 全积 9 块**加**一堆加减，零余量。
**要破**得先加 `mulFull(Wide512)→Wide1024` 这类新 API，`mulHigh` 才有落点
（`h = a₁b₁ + carry(a₁b₀+a₀b₁+carry(a₀b₀))`，全是全积）。

### 墙五：一值一对象，对象头 16 B
JOL 实测：1024 对象 144 B 跨 3 条缓存行；一次 `map.get` 触 6–9 条行。
下游（mc 线）的扁平表已经兑现过随机访问 1.8×、批量 5×。
immutable 对象 API 有个不可约的形；1.7–1.9× 还能靠 `Into`（见候选 D）拿到，再往上必须换形态。

### 墙六：验证粒度不够
混合核笔记本 + 历史上两次"两方案名次互换"（P16 记录）+ 本轮 `mul` 对照组在**没改代码**时漂了 −4.4%。
**我们只能可信地验证 ≥10% 的改动。** 比这小的收益，现有测量体系分不清真假。

## 4. 候选（按"能拿到的倍数"排）

| 候选 | 破哪堵墙 | 机制 | 预期 | 风险 |
|---|---|---|---|---|
| **A. 批量 / SoA 轨道**（新 API，不动现有对象 API） | 三+五+一 | N 对独立乘法 → 进位链互相重叠，从延迟受限变吞吐受限；零分配；bitwise 批量可被 C2 自动向量化 | **mul 2–3×；add/and 3–8×** | 大（新 API），但方向未被证伪 |
| **B. 32 位子肢 + 64 位累加器** | 三 | 把每次进位的 `cmp+setb` 换成 `>>> 32`（BouncyCastle 与 `multiplyToLen` 的机制） | 未知，可能 6.2→3-4 cycle/乘积 | 中；与"64 位肢是硬约定"冲突，**一次都没试过** |
| **C. 对象返回组合**（把 `512.mul` 那条路扩到 768/1024） | 二 | `mulFullDeferred8(...)` 返回对象，让 EA 吃掉中间体 | 分配 672→~144 B；时间 1.1–1.2× | 低（现成 A/B） |
| **D. `Into` 族 + 载体** | 一 | 结果写给调用方 | add/sub/and/shl **1.7–1.9×** | 低（纯增量 API） |
| **E. 离开纯 Java**（FFM + GMP/手写内核） | 三 | 直接用 `mulx`/`adcx` | 2–3×（理论天花板） | 高；设计里"备而不用" |
| **F. `768.mulHigh` 的 `long[12]` 删掉** | — | 纯多余 | −112 B/op，白捡 | 极小 |

## 5. 已被实测封死的方向（别重复提）

- **Karatsuba / Toom 用在低半 `mul`**：见墙四，零余量。
- **宽度层 mul 重组**（按 256 块组合）：本机 431.0 ns / 1328 B，比 monolithic 慢且垃圾 2.4×；工作站上 P16 也是平手。
- **列累加 / 三进位元 / carry-save**：P16 否决（768 +52%，1024 +3%）。
- **单巨方法全开码**：Round H 否决（512/768/1024）。
- **单值 SIMD**：add 没有跨 lane 进位，向量 setup 成本 > 收益；设计已冻结。
- **比较 / 哈希**：0.73 ns 和 4.3 ns、0 分配，已经没余量。
- **"数组当表示层"**：每值 144 → 168 B（更差），多一层间接，且会吃掉 P17 证明的"块直写常数偏移"制胜招；
  更关键——**它救不了 mul 的 528 B scratch**，因为 EA 失败的原因是数组被传进不可内联内核，跟表示层无关。

# 补遗（2026-11-05 深夜，工作站实测后）

> 上面 §1–§7 是**工作站开机之前**的分析，其中的优先级假设被实测部分推翻。以本节为准。

## 已搬上工作站（7950X / JDK21 / 锁核），夹具自证通过

768.mul 69.45 / 768.mulHigh 148.88 / 1024.mul 148.22 / 512.mul 29.49 / 768.add 9.49 —— 与账本逐行吻合，数字可比。

## 四条判决（全部本机实测，非推理）

1. **`mulHigh` 修复成立**：同 run 新旧对拍 375.64 → **266.83 ns（−29%）**，分配不变。
2. **Compiler-Driven SIMD 在单值上等于零**：`-XX:-UseSuperWord` 全算子差 ≤1%
   （add −0.3%、and −0.2%、mul −0.1%、mulHigh 0.0%）。热路径没有可向量化循环，SuperWord 无处下嘴。
   **外部评审把它列为首选方向，在单值形态下被否决。**
3. **`Into` 族不是时间牌**：同一算术三种交付形态（1024）——
   add 8.14(obj) / 8.18(arr,0B) / 9.32(arrToObj)；shl 8.10 / 7.86 / 7.99；**只有 and 赢**（5.82 → 4.17，−28%）。
   分配单价 ≈ 1.65 ns/144 B。所以 `Into` 的价值是 **GC 压力与跨方法 scratch 复用**，不是 CPU 时间。
   （之前"分配占 50–65%"的说法来自笔记本混合核口径，已作废。）
4. **批量重叠只有 1.18×**：两条独立 16 级进位链放同一方法 = 13.87 ns/op（2 次操作），
   单链 8.18；若无重叠应 16.36。**"批量 2–3×"在 add 上不成立。**

## 由此修正的优先级

| 原候选 | 修正后 |
|---|---|
| A 批量/SoA（2–3×） | add 上只有 1.18×；mul 未测，是唯一还可能有空间的（链长得多） |
| D `Into` 族（1.7–1.9×） | 时间口径 1.0–1.4×（仅位运算）；真实价值在 GC/scratch |
| C 对象返回组合 | 时间收益按分配单价折算仅 ~4%（528 B ≈ 6 ns / 148 ns） |
| 外部评审的 SIMD 首选 | **否决**（单值） |
| 新增：768 add/sub 缺口 | **可复现 25–30%**（9.49/9.55 vs 1024 的 8.30/8.45；`and` 正常），值得单独立项 |

## 现在的真问题

单值对象 API 的天花板已经很近了：`add` 8.30、`and` 5.73、`shl` 8.06（1024，都是 ~1.5–2 cycles/limb），
`mul` 148.22 / `mulHigh` 299.30 是它们的一二十倍，且 `mulHigh` 是 5.3 cycle/乘积（内建 ~2）。
**能翻倍的地方只剩 mul/mulHigh，且需要"让多条进位链真正重叠"——而 add 的探针说这件事比想象的难。**

3. 768 比 1024 慢 14%（同代码同结构）——这类"宽度逆序"通常是寄存器分配还是代码布局？怎么系统性定位？

# ScalarWide-FP：基础语义与表示决策

状态：**待逐项确认**。这些定完之后，`p` / `e` 才有意义。

## 0. 先拆开四件事（这是本轮讨论的地基）

| 维度 | 问题 | 是否必须耦合 |
|---|---|---|
| **语义标准** | 算出来的值遵循什么规则（正确舍入、±0、NaN、次正规） | 否 |
| **打包** | 内存里怎么放、序列化成什么字节 | 否 |
| **操作行为** | 哪些运算、哪些舍入模式、是否暴露异常标志 | 部分依赖语义 |
| **特殊行为** | ±0 / NaN / ∞ / 次正规 / 相等与排序的具体规则 | 依赖语义 |

**核心立场建议**：**语义跟 IEEE 754 的"值语义"，位段自己定。**
理由：用户真正依赖的是值语义（`1/3` 舍入到哪、`0*∞` 是不是 NaN），
位段只在"与外部互操作"时才重要，而我们明确不做互操作。

## 1. 语义标准

### 1.1 三个候选

| 方案 | 含义 | 代价 |
|---|---|---|
| **S1 语义对齐 IEEE 754**（推荐） | 值语义与 binary 格式一致：正确舍入、±0、∞、NaN、渐进下溢；但宽度与位段自定 | 必须支持次正规 |
| S2 简化语义 | 无 ±0、无次正规（flush-to-zero）、NaN 单一 | 实现简单约 30%，但用户会遇到"随量级变化的精度断崖" |
| S3 完全自创 | 自己定义一套 | 不可与任何东西对照，测试没有参考 |

**建议 S1。** 理由：正确舍入已经定了是硬要求（决策②），而"正确舍入"只有在
**下溢交给次正规**时才是良定义的；否则"正确"要额外解释"何时 flush"。

### 1.2 需要明确写下的语义承诺

- `+ − × ÷ √` 全为 **correctly rounded**（最近偶数）。
- 下溢**渐进**：结果不足正规精度时进入次正规，而不是归零。
- 上溢 → `±∞`。
- `0 × ∞ = NaN`、`0/0 = NaN`、`∞/∞ = NaN`、`x/0 = ±∞`（x≠0）。
- `(+0) + (−0) = +0`（nearest-even）。

## 2. 打包

### 2.1 关键立场：**内存表示 ≠ 线格式**

| 用途 | 选择 |
|---|---|
| **内存中**（热路径） | **不打包**：`sign` / `exp` / `kind` 是独立字段，有效数 4 肢 |
| **序列化 / 落盘 / 跨进程** | **打包**：定义稳定的字节布局，P6 再定 |

理由：算术每步都要取符号、比指数；打包会让每次访问都变成 mask+shift，
而我们整个整数核的性能哲学就是"扁平字段、零运行时索引"。

### 2.2 不打包的代价（必须承认）

- 对象尺寸略大（多 8 字节左右的 sign/exp/kind 字段，可塞进对象头空档，实际可能免费）。
- **没有 `fromRawBits` / `getRawLong` 这种位级 API**——如果将来要和外部交换二进制，
  必须走"打包/解包"两个函数，而不是直接 reinterpret。

**需要你确认**：能不能接受"没有位级互操作 API"？如果不能，打包就要提前到 P1。

## 3. 操作行为

### 3.1 运算集合与优先级

| 分组 | 运算 | 优先级 |
|---|---|---|
| 核心四则 | `add` `subtract` `multiply` `divide` | **P3** |
| 一元 | `negate` `abs` | P1 |
| 根 | `sqrt` | P5 |
| 融合 | `fma` | P5 |
| 取余 | `remainder`（IEEE 精确余）、`ieeeRemainder` | **P5 之后，可砍** |
| 邻域 | `nextUp` `nextDown` `ulp` `scalb` | P4 |
| 判定 | `isNaN/isInfinite/isFinite/isZero/isNormal/isSubnormal/signBit` | P1 |
| 比较 | `compareTo`（全序）、`compareNumeric`（IEEE 比较） | P1 |
| 转换 | `of(long/double/String)`、`toDouble/toInt/toLong/toString` | P1 / P6 |

**建议**：`ieeeRemainder` 是 IEEE 里最冷门、实现最贵的运算（需要精确商），
**明确放到"不做"清单**，除非你有用途。

### 3.2 舍入模式

| 方案 | 代价 |
|---|---|
| **仅 nearest-even**（推荐） | 测试矩阵 1× |
| 5 种模式（含 toward 0 / +∞ / −∞） | `pack` 多一个 switch（约 +10% 实现），测试矩阵 **5×** |

**建议**：只做 nearest-even，但 `pack` 的签名**预留 `RoundingMode` 参数**（P0 已写）。
将来要加，只改一个函数，不改调用方。

### 3.3 异常/标志（IEEE 的 inexact/overflow/...）

Java 没有可移植的 FP 环境标志。要暴露只有两种做法：
- 每次运算返回 `(值, 标志位)` 的包装 → 破坏 API 简洁、且分配；
- 全局/线程局部粘滞标志 → 非线程安全、隐式状态。

**建议：不暴露。** 若将来调试需要，再加一个 `exact()` 判定（判断本次运算是否有舍入）而不是完整标志。

## 4. 特殊行为

### 4.1 值的语义表

| 主题 | 建议 | 说明 |
|---|---|---|
| **±0** | **保留**（区分 +0 / −0） | 与 IEEE 一致；`1/(−0) = −∞` |
| **NaN** | **单一规范形式**，不区分 quiet/signaling，不保留 payload | 简化；极少数依赖 payload 的用法不覆盖 |
| **∞** | 保留，按 IEEE 规则参与运算 | |
| **次正规** | **支持**（渐进下溢） | 见 1.1 的理由 |
| **NaN 传播** | 任何输入含 NaN ⇒ 输出规范 NaN（包括 `√NaN`、`NaN > x` 的比较结果） | |

### 4.2 相等、排序、哈希（最容易埋坑的一处，必须明确）

参考实现同时提供 `compareTo` 与 `compareNumerically`，说明调用方需要**两种比较**。
建议明确区分三件事：

| API | `+0` vs `−0` | `NaN` vs `NaN` | 用途 |
|---|---|---|---|
| `equals` / `hashCode` | **不相等** | **相等** | map key、缓存（与 Java `Double` 一致） |
| `compareTo` | `−0 < +0` | `NaN` 最大，彼此相等 | 排序、`TreeMap`（**全序**） |
| `compareNumeric` | 相等 | **无序**（返回"不可比"） | 数值比较，对应 IEEE 的 compareQuiet |

**为什么这样分**：`equals` 若把 `+0` 与 `−0` 判等，`hashCode` 就必须相同，
但 `compareTo` 又要区分它们 —— 三者会出现不一致。采用 Java `Double` 的口径最不会被用户误解。

**需要你确认**：是否接受 `equals` 区分 `±0`、且 `NaN.equals(NaN) == true`。

### 4.3 转换的边界行为

| 转换 | 建议 |
|---|---|
| `of(long)` / `of(double)` | **精确**（每个 double 都可表示） |
| `toDouble` | 正确舍入；上溢 → `±∞`；下溢 → `±0` 或次正规（double 的次正规） |
| `toLong` / `toInt` | **饱和**（与 Java 一致），还是抛异常（与 BigInteger 一致）？**需你定** |
| `toString` | P6；先做"指定有效位数"的版本，全精度精确输出可选 |

次级项（由实现方决定，理由随附）：

| 项 | 决定 | 理由 |
|---|---|---|
| `toLong` / `toInt` 越界 | **饱和**（与 Java 的 `double→long` 一致） | 与目标平台默认行为一致，调用方不会意外遇到异常；需要严格语义时改用 `toBigInteger` 路径 |
| `ieeeRemainder` | **不做** | IEEE 最冷门运算，且需要精确商（成本≈一次完整除法 + 精度校验）；`remainder` 也不做，需要时用 `a − trunc(a/b)·b` 组合 |

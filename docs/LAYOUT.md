# ScalarWide 布局测量（JOL）

> 目的：回答 v2 结论 #15–#18（对象头、512 单缓存行、字段顺序、hash 缓存）。
> 工具：`gradlew layout`（test 源集 + jol-core 0.17，`LayoutReport`）。
> 环境：OpenJDK 25.0.3，默认压缩指针（compressed oops）。

## 结果（2026-10-08）

对象头实测 = **8 字节 mark + 4 字节 class + 4 字节对齐间隙 = 16 字节**（所有宽度一致）。

| 宽度 | limb 数 | 数据 | 对象大小 | 头开销 | 占缓存行 |
|---|---|---|---|---|---|
| 128 | 2 | 16B | **32B** | 16B（50%） | 1 行 |
| 256 | 4 | 32B | **48B** | 16B（33%） | 1 行 |
| 384 | 6 | 48B | **64B** | 16B（25%） | 1 行（数据域贴线） |
| 512 | 8 | 64B | **80B** | 16B（20%） | **2 行**（数据域 64B 本身=1 行，头破坏） |
| 768 | 12 | 96B | **112B** | 16B | 2 行 |
| 1024 | 16 | 128B | **144B** | 16B | 3 行 |

## 对 v2 预期逐条裁决

- **#15 "Wide128 数据 16B、头 16B、50% 浪费"** → **实测确认**（32B 对象）。
- **#16 "512 是单缓存行上限：8 limb=64B 正好一行；对象头是唯一破坏者"** → **实测确认**：
  数据域 64B = 1 行，但对象 80B 必然跨 2 行。**要兑现单行只能靠 SoA / Valhalla**（Java 现状：SoA）。
- **#17 字段顺序（低 limb 在前）**：`compareUnsigned` 从 l15 起比对——在 1024 档 l15 位于
  对象尾部（offset 136，第 3 行），比较通常只触该行。高 limb 前置可把"热点行"换成第 1 行，
  但收益限于 768+ 且需 A/B 实测（已挂账，不先做）。
- **#18 hash 缓存成本（供决策）**：加一个 `int` 缓存字段——Wide128 32B→40B（**+25%**）、
  Wide256 48B→56B（+16.7%）、512 80B→88B（+10%）、1024 144B→152B（+5.6%）。
  小宽度不划算、大宽度便宜；与"SoA 里 hash 作为独立列"相比对象内缓存增益有限。

## 热工作集换算（对象 API 口径）

- 100 万个 256 位 key 的对象数组：48B/对象 + 8B 引用 ≈ **56MB**（对比数据本体 32MB）；
- 若走 SoA（32B 数据 + 4B hash 列 + 稀疏表）：≈ **36-40MB**——"塞进 L2"的目标只在
  热工作集足够小（几万 key）时由 L2 承接；对象头在其中占 1/3 的存储预算。

## 决策记录（2026-10-08，依据上表 + 锁核 hash 基准）

- **hash 缓存：不缓存。**
  - 实测（锁核，15×）：本库 hash 计算 128 = **0.892ns**、256 = **1.344ns**；
    BigInteger（自带缓存）同场 2.248 / 3.549ns——我们仍快 2.5×。
  - 缓存读 ≈ 0.3-0.5ns，净省 ≈ 0.4-0.9ns/调用；代价 +8B/对象（128 +25%、256 +16.7%）。
  - 判决：**不值**。映射层若需要，用 SoA 的 4B hash 列（不破坏对象布局）。
  - CSV：`BENCH-2026-10-08-hash-decision.csv`。
- **字段顺序（高 limb 前置）：维持现状（低 limb 在前）。**
  - 潜在收益仅限 768/1024（跨行对象），且热循环中行通常常驻缓存；收益 ≲1ns 级。
  - 触发条件：真实剖析显示 `compareUnsigned` 出现缓存缺失时再做两版 A/B。
- **SoA 轨道（挂账）**：触发条件 = 映射层进入实现（库内不再无场景预做）。
- **进位保存链内延迟研究（挂账）**：触发条件 = 真实 workload 剖析显示 `mulFull` 链延迟为瓶颈。

## 比较体系 v2（2026-10-14 · issue #1 两轮审议后定稿）

社区审议（InfGithub）两轮意见均成立，本仓正式废弃"Wide vs BigInteger 性能对照"体系：

1. **BigInteger = 正确性 oracle，仅在测试套件中用于对拍**（差分/互操作/除法 oracle 等）。
   性能基准中不再出现任何 BigInteger 对照（已从 `src/jmh` 全面移除，含此前的"截断构造"
   `bigMulLow` 等——该操作不表达任何真实用途，属错误的补救，一并废弃）。
2. **性能对照只有两类**：
   - ① **同场景加速库**：定宽 limb 算术 = BouncyCastle `math.raw.Nat*`（见下节）；
     键/映射场景 = fastutil/JDK 实现；
   - ② **本库版本前后对比**（BENCH 账本原有主体形态）。
3. **记录主体 = 绝对 ns/op + 分配（`-prof gc`）**；比值均为参照。
4. **历史存证**：本文件 2026-10-14 之前的全部 `vs BigInteger` 比值一律视为历史存证
   （不作结论）——不回填、不删除（只记录现象纪律）；其中 `mul`(低半) vs `bigMul`(全积)、
   `add/sub` vs 裸 big、`shl` vs `bigShl` 等亦非同映射，双重不构成判决。
5. 场景级探针（Pipeline/Batch：键映射与批量工作集）中 `HashMap<BigInteger>` 作为
   **场景候选实现**保留并标注——那里对照的是"键类型架构选择"而非算术。

### 同场景对照：Long2 0.1.8（1024 档 18 项全对拍）

**7 胜 / 8 平 / 3 负**（同 run 同 JVM；`CompetitorBench`）：

- **领先**：`hash` **29.4×**、`toHexString` **3.68×**、左移 **3.62×**、右移 **2.21×**、
  `bitLength` 1.16×、`neg` 1.6%、`toString` 2.5%
- **持平**（±2.8%）：`and` / `or` / `xor` / `not` / `compareTo` / `bitCount` / `toLong` / `add`
- **落后**：`multiply` **10.0%**（参数空间已扫穿）、`sub` 6.1%、`equals` 4.0%
  （后两项在本机噪声包络内）

**能力面**：`mulHigh` / `mulFull`（128/256/512 三级）/ `div` / `rem` / `pow` / `min`/`max`/`abs` /
无符号与有符号双比较 —— Long2 均无（它只有回绕乘法与若干转换）。

### 一句话结论（`v1.0.1`）

**按 map 键的场景打，我们赢（hash 领先 29×、序列化领先 1.5–3.2×）；按"纯算一个大数乘法"打，
我们差 10%；按功能面打，我们多一层。** 剩余唯一真缺口是 1024 `multiply` 的 10%——
它的参数空间（分块点 / 列内拆分 / 分带 / 局部变量）已全部实测覆盖，落在 89–107 ns，
**这 10% 属 HotSpot 对 `mulx`/`mulhi` 的寄存器分配差异，Java 侧无可调旋钮。**

### 同场景主对照：BouncyCastle 定宽 limb 算术（2026-10-14，issue #1 后续）

- 动机（社区审议的实质）：对照要与**同类设计场景**的加速库做——定宽整数算术内核，而不是
  给 BigInteger 打截断补丁。BigInteger 退回 oracle。
- 对照对象：`org.bouncycastle.math.raw.Nat128/Nat256`（专用）、`Nat384`（仅 mul 专用）、
  `Nat.add/sub`（512+ 通用，BC 无 Nat512/768/1024 专用类）；`bcprov-jdk18on:1.78.1`，
  **仅 jmh 作用域**（不进库产物）。BC = 32 位 limb + 预分配 `int[]`；我们 = 64 位 limb +
  immutable 对象 API / Mutable 载体。
- 口径：**只收同映射操作**——`add/sub` 全宽度（模 2^N）；`mulFull` 仅 128/256（我们 384+ 无
  2N 位结果类；已实测 BC `mul` 写 2N 字全积，与 `mulFull` 同映射）。BC 无低半积 API ⇒
  半积不列（不造非映射对照）。
- 基准：`NatCompareBench`；CSV `BENCH-2026-10-14-nat-compare.csv`（时间）与
  `BENCH-2026-10-14-nat-alloc.csv`（`-prof gc`）。
- 环境：工作站 DESKTOP-8ADRQTA（7950X）Windows / JDK 21.0.3 / `-wi 5 -i 10 -f 1 -w 1s -r 1s`
  未锁核；commit `e8132e7`。

## 2026-10-08 · 附魔轮 1（0.1.0 → 0.2.0，锁核权威）

**测量方法（本轮升级）**：混合核 CPU（Ultra 7 155H）上，JMH 逐基准 fork 的调度漂移
使 BigInteger 对照组跨 fork 抖动达 1.4–1.7×（误差 ±60%，见下节）。故本轮改用
**CPU 亲和锁定**：`cmd /c start /b /wait /affinity 1` 启动 JMH runner jar（fork 子进程继承亲和），
固定逻辑核 0；`-wi 5 -i 10 -f 1 -w 500ms -r 500ms`。误差棒降至 ±2~10%。

- 命令（前/后同一命令，仅换 jar）：

```
cmd /c start "sw" /b /wait /affinity 1 "<jdk25>\bin\java.exe" -jar "<before|after>.jar" "(Wide128Bench|Wide256Bench)\.(add|sub|mul|and|shl|ushr|bigAdd|bigSub|bigMul|bigAnd|bigShl|bigUshr)$" -wi 5 -i 10 -f 1 -w 500ms -r 500ms -rf csv -rff docs\BENCH-pinned-<before|after>.csv
```

- jar 来源：`gradlew jmhJar`。before = 0.1.0 行为等价构建（被测运算与 0.1.0 相同代码路径：
  `Limbs` 引擎 + pack/unpack 数组）；after = 0.2.0 寄存器化/展开版。同机同会话，先后测量。
- 数据：`BENCH-pinned-before.csv`、`BENCH-pinned-after.csv`。

  已被 JIT 逃逸分析消去中间数组，前值（~2.6 ns）已接近"单次对象分配"下限。
- **对 BigInteger 的比值**：128 为 3.0–5.9×，256 为 2.5–2.8×。
  **验收线（256 加减 ≥5×、位运算 ≥8×）尚未达标**；剩余瓶颈 = 结果对象分配（每调用 1 次），
  归附魔轮 2（零分配 API）。hash/compare 0.1.0 起就是直算，未纳入本轮对照。

## 2026-10-08 · Round B：512 `mulHigh` 攻坚（0.6.1 → 0.6.2，锁核）

用户拍板"没那么快认输"，继续攻。尝试轨迹（每步都测）：

1. **错误恒等式**（误删 aL·bL 的贡献）→ 对拍当场抓住（差 1~2）→ 废弃。
2. **两段法**（prepHigh 预算内 + 轻量组合）→ 分配 **832 → 480 B/op**；时间 148 → 144ns（不变）。
3. **全开码单方法**（4 季积 + limb 级进位一体化，零中间对象）→ 分配 **480 → 80 B/op**
   （EA 完美，与 `mul` 同级）；途中对拍又抓住一处漏加 hh 低 4 limb 的进位 bug。

现状（锁核，同 run 对照；CSV：`BENCH-2026-10-08-roundB-before/after.csv`）：

| 基准 | 0.6.1 | 0.6.2 | 对照（0.6.2 run） |
|---|---|---|---|
| Wide512.mulHigh | 148.1ns / 832 B/op | **137.5ns / 80 B/op** | bigMul 86.4ns |
| Wide512.mul | 48.7ns | 53.9ns | — |

结论（仅限本条件）：
- **分配问题解决**：832 → 80 B/op（10×），与 `mul` 同级——对 GC 噪声/吞吐是实质改善。
- **时间仍差 bigMul 1.6×**：137 ≈ 4 × 34.9ns（`Wide256.mulFull` 单测值）——四个季积的
  独立链没有被 ILP 重叠（疑似 JIT 调度/寄存器压力），需 `-XX:+PrintAssembly` 级剖析。
- **三路对拍两次守门**（错误恒等式、漏 limb）——验证体系再次兑现。

### Round B 附注：ILP 判决（决定 Karatsuba 是否值得）

| 基准 | ns/op | 分配 | 解读 |
|---|---|---|---|
| mulFullOne（1 个完整季积） | 32.3 | 80 B/op | 单链真价（8 列串行进位） |
| mulFullTwo（2 个独立季积） | 65.4 | 80 B/op | = 2.02×；**链间零重叠** |
| mul（3 季积） | 53.2 | 80 B/op | m1/m2 只活低 256 位 → JIT DCE 砍链 |
| mulHigh（4 个全宽季积 + 进位趟） | 143.4 | 80 B/op | = 4×32.3 + 趟 ✓ |

- **结论**：`mulHigh` 的地板 ≈ 137ns = 4 条满宽串行链 + 进位趟，链间无 ILP。
- **Karatsuba 预期收益 ≈ 0**（数据否决）：省 1 条链（−32ns），但溢出位修正 + 2 次宽减法 +
  进位重算 ≥ +30ns（按本机每次宽操作 ≈ 8 链步的汇率）。
- 若要再进一步，唯一方向是**链内延迟优化**（进位保存/冗余表示），属研究级重写；当前接受
  137ns / 80 B/op 为 512 `mulHigh` 的标量现状。

## 2026-10-08 · Round F：零分配载体 API 首测（0.10.0，锁核 + -prof gc）

- 设计决策：零分配 API 采用 **Mutable 载体（*Into 对象风）**——`MutableWide128/256`

  永不做 key；线程不安全）。
- 公平对照（同为 3 步链：set→add→mul→add）：

| 基准 | ns/op | 分配 |
|---|---|---|

| mutableChain（载体链） | 17.51 | 48 B/op（同上，载体在 setup 一次） |

| hashSequential4（4 次朴素 `hashCode` 调用） | 4.331（1.08ns/个） |

- 结论：**手工批窗口无收益**——JIT 会把可内联的链自动交错（4.33 < 4 x 1.34，天然含
  ~1.24x 免费重叠）；手工交错反而多占寄存器。批循环天然吃 ~1.1x/op，不需要新 API。
- 与旧数据互证：大链不可内联 → 不重叠（Round H/ILP）；小链可内联 → JIT 自动窗口化。

  2. `toString`/`toHexString` 白捡 21%–29%——它们只是 `toBigInteger()` 的下游，本轮未单独改动；
  3. 剩余分配 ≈ 128 B 字节数组 + BigInteger 本体 + `pack()` 的 144 B limb 数组。**`pack()` 是下一档
     理论余量（≈144 B/op），但时间余量已很小，本轮不取**（一次一变量）。
- 顺带记账（Round 0 新增覆盖）：`ByteIoBench` 补 768/1024 两档（原覆盖只到 512）——
  toBytes128/256/512/768/1024 = **9.1 / 15.9 / 29.6 / 44.7 / 56.2** ns，toBytesFixed1024 = 43.0 ns；
  fromBytes128/256/512/768/1024 = **20.4 / 33.6 / 68.7 / 99.3 / 131.0** ns；
  编码侧分配 = 字节数组本体（32/48/80/112/144 B），与 P17 的线性结论一致。
- 测试：全量 `gradlew test` 绿（`toBigInteger` 的符号/零/极值语义由既有差分管住）。

## 2026-11-05 · 诊断（main）：256+ 的每 op 分配账——scratch 逃逸

- 目的：为"128 全内联之后，256+ 还能往哪压"定位。只记现象与机制，不改代码。
- 环境/命令同上一节（锁核、`-prof gc`）；CSV：`BENCH-2026-11-05-w512-768-gc.csv`、
  `-w1024-gc.csv`。分配列误差棒 0.001 B/op，**与机器无关，可直接跨机比对**；时间列仅本机。

| ns/op · B/op | 512 | 768 | 1024 |
|---|---|---|---|
| add | 9.86 · 80 | 14.37 · 112 | 15.22 · 144 |
| sub | 9.53 · 80 | 14.39 · 112 | 16.19 · 144 |
| and | 7.72 · 80 | 11.42 · 112 | 13.64 · 144 |
| shl / ushr | 8.31 / 8.54 · 80 | 12.59 / 12.41 · 112 | 14.93 / 15.23 · 144 |
| **mul** | 37.11 · **80** | 106.0 · **416** | 203.1 · **672** |
| **mulHigh** | 92.0 · **352** | 220.7 · **816** | 529.6 · **416** |
| compare | 0.72 · 0 | 0.73 · 0 | 0.75 · 0 |
| hash | — | 3.55 · 0 | 4.31 · 0 |

- 观察（仅限本条件，R10）：
  1. **add/sub/and/shl 的分配恒等于结果对象本体**（BITS/8+16）——EA 干净。这几项在 1024 档
     `and`（16 条 ALU 指令）也要 13.6 ns，说明它们**已不是 ALU 受限，而是分配 + 写回受限**。
     这也是 BENCH §2026-10-14「768/1024 add 落后 BC Nat 15–25%」的第一嫌疑：BC 是零分配的
     数组内核，我们是"每次一个结果对象"——**同一算术、不同 API 形态**。
  2. **512 `mul` 是 80 B/op（只有结果对象），768/1024 `mul` 是 416/672 B/op** ——同库同原子、
     两条不同组合路径的天然 A/B：`512.mul` 走 `mulFull` 返回对象（EA 友好），
     `768/1024.mul` 走 `mulFullInto8(s,…)` 传入 `long[N]` scratch。**`mulFullInto8` = 1509 B
     不可内联（P7）→ scratch 逃逸 → EA 失效**，剩下的全是纯垃圾：768 多 304 B、1024 多 528 B。
  3. **`mulHigh` 病最重**：768 竟达 **816 B/op**，1024 529.6 ns/416 B。且时间随宽度超线性——
     512→768→1024 = 92 / 220.7 / 529.6，宽度比 1.5/1.33 而时间比 2.4/2.4，O(N²) 应给
     2.25/1.78。**1024 比二次还慢 35%**，属账上从未记录的异常（P7 记录的 311.9 ns 是工作站
     JDK21 口径，同机同口径不可比）。
  4. `compare`（0.73–0.75 ns，0 分配）与 `hash`（3.6–4.3 ns，0 分配）**已经没有余量**，
     不要在比较/哈希上继续找收益。
  5. 本机 768/1024 的 `add` 与 `sub` 同速（14.37/14.39、15.22/16.19），**工作站的「768/1024 add
     异常」在本机不复现**——该现象确系布局运气，不是结构缺陷。

## 2026-11-05 · Round 3（main）：1024 `mulHigh` 内层去 switch——−30.6%

- 诊断起点：`Wide1024.mulHigh` 是全库**唯一**还在循环体内用运行时索引访问器的热方法——
  `for (i) { ai = limb(i); for (j) { bj = o.limb(j); … acc[i + j] … } }`：
  每次调用进 **272 次 16-way `limb` switch**（其中 256 次在最内层）。三条自家教训被同时违反：
  P17「动态长度循环 + 运行时索引访问器 = 杀手」、P7「`o.limb(i)` 作实参是主要浪费」（该修复
  只落到 `mul`，没落到幸存的 monolithic `mulHigh`）。
- 改动：内层循环**展开为 16 段直读字段**（`o.l0`…`o.l15` 常量偏移），外层保留；语义逐语句等同。
- 环境/命令同上节（锁核 + `-prof gc`）；CSV：`BENCH-2026-11-05-mulhigh-b.csv`；
  诊断对照 `-mulhigh-diag.csv`、被弃中间版 `-mulhigh-a.csv`。

| Wide1024（pinned，同机同命令） | 改前 | 改后 | 变化 | B/op |
|---|---|---|---|---|
| **mulHigh** | 529.6 ± 11.6 | **367.8 ± 11.6** | **−30.6%（1.44×）** | 416 → **416** |
| mul（对照组，未改代码） | 203.1 ± 3.3 | 194.1 ± 6.6 | −4.4%（噪声/布局） | 672 → 672 |

- 中间版本与被弃方案（同 run 内对照，故可直接比）：
  - 「把 `o` 的 limb 提到局部 `long[] b`」→ **392.6 ns / 560 B**：时间对了，但白扔 144 B；
  - `mulHighComposed`（9 块 + 直读字段）→ **431.0 ns / 1328 B**：**比 monolithic 更慢且垃圾 2.4×**，
    独立复现 P16 的否决（工作站上是 365.7 vs 354.5，本机差距更大）。
- 观察（仅限本条件，R10）：
  1. 收益全部来自消掉 272 次间接跳转（16 目标 jump table，间接分支预测≈50%），不是来自算术；
  2. 时间 367.8 ns / 256 个乘积 = **6.2 cycle/乘积**（4.3 GHz 折算），仍远高于 `multiplyToLen`
     内建的 ~2 cycle——**残余是行内 16 级串行进位链的延迟**，不是吞吐。P16 的列累加已证明
     打断这条链（三进位元）在 Java 里会因活跃值溢出寄存器而无收益；本机 composed 431 ns 亦同向。
  3. 因此 1024 `mulHigh` 的下一档不在这条路线；要动只能动「让 scratch 不再上堆」（见诊断节观察 2），
     而那是 `mulFullInto8` 内联问题，不是 `mulHigh` 自身结构问题。
- 测试：`MulHighInternalTest`（`mulHigh` vs `mulHighComposed` vs BigInteger 移位，含 MAX/ZERO/
  固定对）全绿；`Wide1024Test` 全绿。

## 2026-11-06 · 工作站：批量重叠探针——**批量路线否决（负结果）**

- 待答问题：单条 16 级进位链是延迟受限（`mulHigh` 5.3 cycle/乘积 vs 内建 ~2）。批量（SoA / N 路交错）
  是唯一还能打断延迟链的机制——**若多条独立链能重叠，乘法就有 2× 以上的空间**。
- 夹具 `BatchOverlapBench`：`mulHigh` 的 1 / 2 / 4 条独立链，逐行显式交错；`@OperationsPerInvocation(k)`
  把时间归一成 **ns/结果**。
  **读法**：零重叠 ⇒ ns/结果 与 k 无关；吞吐受限 ⇒ ns/结果 随 k 下降到最多 1/k。
- 环境同上节（7950X / JDK21 / 锁核 / `-prof gc`）；CSV `BENCH-2026-11-06-ws-batchoverlap.csv`。

| 形态 | ns/结果 | B/op | 相对 mh1 |
|---|---|---|---|
| mh1（1 链，循环版） | 273.06 | 0 | 1.00 |
| mh2（2 链交错） | 375.92 | 0 | **1.38（更差）** |
| **mh4（4 链交错）** | **263.18** | 0 | **0.96** |
| mhProd（生产实现锚点） | 276.11 | 416 | 1.01 |

- **判决：批量重叠 = 0。** 4 条独立链的每结果代价与 1 条链持平（263 vs 273，−4%）——即
  **4 个结果花了 4 倍时间**，没有任何吞吐收益。2 链反而退化 38%（非单调，判为代码布局噪声，
  只读端点结论）。
- 机制判读：链内每一步是 `acc[k]` 的 **load → add → cmp → add → cmp → store**，下一步依赖上一步的
  store-to-load forwarding（~4–5 cycle）。4.8 cycle/乘积 ≈ 该往返延迟本身。
  **瓶颈不是指令吞吐，是"累加器每步过一次内存"**；而 Java 里让 JIT 证明不同链的数组互不别名
  做不到，所以源码级交错也换不来并行。
- **副产物（重要）**：`mh1`（循环版单链，273）≈ `mhProd`（生产实现，手工展开内层，276）——
  **展开与否没有差别**，乘法的代码级微优化已经到底；276–299 ns 就是这种
  "累加器走内存的 64 位肢串行 schoolbook" 的硬件地板。
- 由此关闭的路线：批量/SoA 内核（本探针）、单值 SIMD（同日前一条，实测 ≤1%）、
  Into 的时间收益（同日判决 3）、宽度层重组 / 列累加 / 单巨方法（P16 / Round H）。
  **批量本是 SIMD 唯一的落点，两者同时出局。**

| both | 1.038 | 0.840 |
| twoLo（CSE 对照） | 0.372 | 0.174 |

  `both ≈ lo + hi` ⇒ **每对必须两条乘法指令**，"配对原语"在纯 Java 下不可实现（需改 HotSpot）。
  副产物：`mulhi` 单价是 `a*b` 的 **3.7×** ⇒ 少要一个高半比少要一个低半值钱得多。
- 靶子换算：`mul` 的**乘法指令数**我们 320（160 对同操作数各发两条）vs Long2 **256**
  （136 个 lo + 120 个 hi）——只差 1.25×，而实测差 1.84× ⇒ 另一大半是**每条指令的效率**
  （2.1 vs 1.3 cycle），来源即已记录的 scratch 落堆与装配。
  **地板 ≈ 256 × 1.3 cycle ≈ 74 ns**；Long2 是其 92%，我们 50%。**目标 80–85 ns（1.8×）。**
- 观察（仅限本条件，R10）：
  1. 我们的 `and` 与他们持平、`hash` 快 2×、`add` 慢 19%——**短板集中在乘法**；
  2. 但消费侧（G2/mc）热路径**根本不调 multiply**（键构造/比较/哈希/序列化），
     所以这 1.9× 是**库的征信问题**，不是 G2 首屏的问题；
  3. 其内核形态与我们 P16 否决过的"列累加"同族，但**活集只有 O(1)**（一次一列，2 个寄存器），
     而 P16 版是 3 进位字 × 16 列 = 48 活值 ⇒ 溢出。**负面结果要连"活集"一起记，否则会误判整个方向。**

## 2026-11-06 · Round 4（main）：`Wide1024.mul` 改列累加内核——153 → 103.6 ns（−32%）

- 动机：上一节实测我们 1024 `mul` 落后 Long2 1.90×，差距在**乘法指令数**（320 vs 256）与
  **每条指令的效率**（2.1 vs 1.3 cycle）。本轮把 `mul` 换成列主序内核。
- 形态（**我们自己的写法**，非移植）：列 k 的项 = `lo(a_i,b_j)` 满足 i+j=k，加上 `hi(a_i,b_j)`
  满足 i+j=k−1；每列用一对寄存器（`u` 累加和 + `q` 溢出计数）并在列末**写一次** `r[k]`，
  `q` 作为下一列的入进位。1024 档共 **136 个 lo + 120 个 hi = 256 条乘法指令**。
- 生成器：`tools/gen-colmul.ps1`（按位宽/分块数参数化，直接拼进源码；`build/gen/` 留副本）。
- 环境：7950X / JDK 25 / 锁核 LP0 / `-wi 5 -i 10 -f 1 -w 500ms -r 500ms -prof gc`。
  CSV：`BENCH-2026-11-06-ws-colmul.csv`；夹具 `CompetitorBench`（两库同 run，环境漂移对双方同乘）。

| ns/op | 旧内核 | **列累加** | Long2 0.1.8 | ours/Long2 | B/op |
|---|---|---|---|---|---|
| **1024 mul** | 153.13 | **89.41 ± 0.22** | 80.83 ± 0.20 | **1.11×**（原 1.90×） | 672 → **288** |
| 1024 add / and | — | 8.19 / 5.72 | 7.52 / 5.70 | 1.09× / 1.00× | 144 |
| 1024 hash | — | **4.96** | 10.37 | **0.48×** | 0 |
| 256 mul | 6.91 | 6.91（未改） | 4.34 | 1.59× | 48 |

- **分块数是本轮最大的单一变量**（同机同命令，只改 `-Groups`）：

| 分块 | 方法数 | 列/块 | 最大块项数 | ns/op | 判定 |
|---|---|---|---|---|---|
| 4 | 4 | 4 | 112 | 103.63 | 可用 |

  恰好把内核劈成两个方法——**不是风格，是硬限制**。
- 观察（仅限本条件，R10）：
  1. 分配从 672 → **288 B/op**，与 Long2 持平——`long[64]` scratch 退化成 `long[16]` 结果缓冲。
  2. **踩到一个此前没记过的硬限制**：单方法 876 行触发 HotSpot `HugeMethodLimit`，**C2 直接不编译**，
     全程解释器 → 7765.9 ns（慢 50×）。**规程：生成式内核必须按字节码尺寸分块，分块后必须复测。**
  3. 残余 1.11×（89.4 vs 80.8）：我们每条乘法指令 1.55 cycle、Long2 1.40 cycle。
     分块已到边界（再少就不可编译），剩下的只能从**列内表达式**上找（如 `q` 的更新方式、
     `carry` 的引入时机）。
  4. `256.mul` 中途一跑测得 10.37（代码未改），复核回到 6.913——**布局敏感，单跑不作结论**；
     `1024` 的 1.11× 是同 run 对拍，不受影响。
- 正确性：全量 `gradlew test` 绿（`Wide1024Test` 的极值 + 种子 12345 差分 vs BigInteger 全覆盖）。

## 2026-11-06 · Round 11（main）：`mulHigh` 列内双累加器——全线再降 4–15%

- 机制：一列最多 **2N−1 = 31 项**，原来的 `q` 进位链是 31 级**串行**依赖。把每列的项拆成两条
  独立链（`u/q` 与 `v/q2`）再合并一次，临界路径减半，代价是每列多 ~3 条合并指令。
  数学等价：`ΣA + ΣB + carryIn` 的进位 = `q + q2 + ovf(u+v) + ovf(..+carryIn)`。
- 生成器参数 `-Split 2`。**首次实现是错的**：用 scriptblock 传"写目标表达式"，多块路径下
  动态作用域导致列索引映射退化成 `0,3,6,…`（周期 = 分块数），差分门禁以
  `ArrayIndexOutOfBoundsException` 当场抓住并回退。改成**直接传字符串**（`Get-Dest`）后正确。
  **教训：生成器里不要用闭包传"指令"，传值。**

## 2026-11-06 · Round 12（main）：hash 懒缓存——1024 提速 14.1×，且**零字节代价**

- 起因：`hash` 是 map 查找的关键路径。逐宽度实测其成本（工作站，JDK 25）：

| 宽度 | hash ns（改前） | **ns/肢** | 改后 | 倍数 |
|---|---|---|---|---|
| 128 | 0.727 | 0.36 | **0.351** | 2.07× |
| 256 | 1.252 | 0.31 | **0.350** | 3.58× |
| 768 | 3.527 | 0.29 | **0.352** | 10.0× |
| 1024 | 4.982 | 0.31 | **0.353** | **14.1×** |

- **`LAYOUT.md` 的立论前提是错的，已订正。** 它按"加一个 `int` 字段 = +8 B"算出
  128 +25% / 256 +16.7%，据此判"不缓存"。但 JOL 实测：`int hash` 落在 **offset 12** ——
  对象头 8B mark + 4B class 之后那 **4 字节对齐空档**，六档实例尺寸全部不变
  （32 / 48 / 64 / 80 / 112 / 144 B）。**这个字段是零成本的。**
- 因此先前"128 会因为每缓存行从 2 键掉到 1 键而倒亏"的推断也一并作废——32 B 仍是 32 B。
- 实现：**懒加载**（`hash == 0` 时算一次；0 作哨兵，算出 0 时取 1）。不用饿汉式，因为
  `mul`/`mulHigh` 的结果不会被 hash，不该在构造时付这条乘法链。
  并发写是良性竞争：两个线程算出的值相同。
- 验证：`mul` 1024 = 89.269（改前 89.37）、`mulHigh` = 166.293（改前 166.16）、`256.mul` = 4.671
  —— **算术零回归**；`gradlew layout` 六档尺寸不变。
- 观察（仅限本条件，R10）：
  1. 缓存后 hash 与宽度**无关**（0.350–0.353 ns），本质上退化成一次字段读。
  2. **树形 hash 无用**：每肢成本在所有宽度上都稳定在 0.29–0.36 ns（≈1.4 cycle），说明它是
     **吞吐受限**（`imul` 1/cycle，JMH 相邻迭代可重叠），不是延迟受限——换形状不减少乘法条数。
     **所以 hash 只有缓存一条路。**
  3. 哨兵改写：算出的 hash 为 0 时返回 1（概率 2⁻³²），`hashCode` 契约只要求一致性，成立。

## 2026-11-06 · Round 15（main）：进位改「单比较」——add 全线 1.09–1.75×，已反超 Long2

- 成因：我们的进位是**每肢两次比较**（`cmp(s,a)` 与 `cmp(r,s)`），Long2 是**一次比较**——
  `r <u a` 与 `r == a` 出自同一条 `cmp`，两个条件码都免费。
- 改动：每肢的
  `s=a+b; r=s+c; c=cmp(s,a)+cmp(r,s)`
  换成
  `r=a+b+c; c = (r <u a) || (c!=0 && r==a)`
  （减法对称：`r=a-b-br; br = (r >u a) || (br!=0 && r==a)`）。这是标准进位恒等式，
  第二项极少触发、分支高度可预测。脚本 `tools/patch-carry.ps1`；`Wide128` 无需改（2 肢已是单比较）。
- 环境：7950X / JDK 25 / 锁核 LP0 / `-wi 5 -i 10 -f 1 -w 500ms -r 500ms`。

| 256 | 2.412 | **1.862** | 1.30× | 1.897 | **1.874** | 1.01× |
| 384 | 4.172 | **2.381** | **1.75×** | 3.952 | **2.428** | 1.63× |
| 512 | 5.411 | **3.625** | 1.49× | 5.352 | **3.618** | 1.48× |

## 2026-11-06 · Round 17（main）：寄存器窗口「分带并行」结构——**实测否决（负结果）**

- 机会点：列累加是"一次一列、列内串行"。若把连续 B 列**同时**累加（每列一对寄存器），
  再统一做一次 B 步进位扫，就能拿到 B 条独立链的 ILP。B=1 退化成现有结构，所以它覆盖整个设计空间。
- 实现：生成器 `-Band B`（默认 1）。1024 / MaxTerms 180 / Split 1 扫描：

| 结构（1024 mul） | ns |
|---|---|
| **列累加 + Split=2（Band=1）** | **88.96** ✅ |
| Band=2 | 96.99 |
| Band=8 | 101.89 |
| Band=4 | 107.32 |

- **判决：分带并行全面劣于"列内拆分"。** 两者都在制造独立进位链，但代价不同：
  - 列内拆分：一条列内**仍是 2 条链**，活跃值 ≤4，且列的写回时机不变；
  - 分带：B 列的累加器**同时存活**（2B 个活值）⇒ 寄存器压力上来，且每个带都要把两操作数的
    整段 limb 重新读一遍 ⇒ 访存变成 B 倍。
- 附注：**"造并行"这件事已被穷举**——列内双链（有效，1.15×）、分带（无效）、
  批量交错（无效，Round 4）、列累加本身（有效）。四条路的结论互相独立但一致：
  **收益来自"减少串行依赖"，而"增加同时存活的链数"一旦越过寄存器预算就反噬。**
- 踩坑：`foreach ($band ...)` 把生成器参数 `$Band` 覆盖成数组（PowerShell 大小写不敏感），
  本轮第二次犯这一类错（上次是 `$groups`/`$Groups`）。**规程：PS 脚本里局部变量不得与参数同名（忽略大小写）。**

  1. 最小长度版比定宽版贵（8.26 vs 5.68），差额 = `bitLength()` + 变长数组 + 头部收尾。
     这是**语义决定的**，不是实现浪费。
  2. LE 比 BE 快 21%（6.52 vs 8.26）：BE 要倒着写且头部要从最高肢取，LE 只需顺序写 + 尾部补。

- **测试覆盖的真实盲区（已补）**：原 `ByteIoTest` 只喂 `new BigInteger(bits, rnd)`，
  这类值字节长恒为 8 的倍数 ⇒ **`rem` 恒为 0 ⇒ 头部路径从未被执行**。
  新增 `MinimalBytesTest`：六宽度 × **位长 1..N 全扫**（3072 个值）+ 边界（0/1/max/min-bit/
  每个 `rem` 的 2^k 与 2^k−1/单肢值）。
  **并用变异测试证明门禁会响**：把头部移位 `8*(rem−1−j)` 改成 `8*(rem−j)`，两个用例当场变红。

### 二、`Wide384.mulFull(Wide384) → Wide768`（纯增量）

- 全积阶梯原来只有三级（128→256、256→512、512→1024），**384 缺一档**，而 384 的全积正好是
  768 位（有现成类型）。生成器 `-Mode full` 直接产出。

| 384 档 ns | 值 |
|---|---|
| `mul` | 11.126 |
| `mulHigh` | 17.315 |
| **`mulFull`（一次算全 12 肢）** | **21.050** |
| 分开算 `mul` + `mulHigh` 之和 | 28.441 |

- **全积比"两半分别算"快 1.35×**（与 512 档的 1.25× 同向，机制相同：只走一遍列累加，
  不必为高半重算整条进位链）。
- 正确性：`MulFullTest` 新增 `wide384FullProductMatchesBigInteger`（极端值两两 + 2000 对种子随机，
  vs BigInteger，并逐肢校验与 `mul`/`mulHigh` 一致）。


## 2026-11-06 · Round 19（main）：`bitLength` 拆快路径——1.150 → 0.382 ns（3.01×）

- 成因：`bitLength()` 是从最高肢起的 16 段 `if` 链，**字节码约 480 B，远超 325 B 热内联阈值**
  ⇒ 从未被内联进调用方（对方 0.442 ns 说明地板只有 ~2 cycle，我们 1.150 = ~5 cycle，差额正是调用开销）。
- 改动：拆成两段——`bitLength()` 只看最高肢（~30 B，必内联）+ 非内联的 `bitLengthTail()`
  保留原自顶向下链。稠密值（最高肢非零）走内联快路径；稀疏值多付一次调用，
  与拆分前打平（拆分前同样没被内联）。
- 环境：7950X / JDK 25 / 锁核；夹具 `CompetitorBench`。

| 1024 | 改前 | **改后** | 倍数 | Long2 | 改后比值 |
|---|---|---|---|---|---|
| `bitLength` | 1.150 | **0.382** | **3.01×** | 0.441 | **领先 1.15×**（原落后 2.60×） |

- 观察：**这是一条可复用的通用规律**——"分派链过长 ⇒ 越过 325 B ⇒ 永不内联"。`bitLength` 不是孤例，
  任何"多分支小算子"都该按这个模式拆（快路径内联 + 尾链外置）。
